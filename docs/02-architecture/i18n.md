# i18n.md — Internacionalización

Documento narrado de la arquitectura de internacionalización del proyecto: qué existe, por qué
se decidió así, y cómo se extiende a futuro. Complementa, sin repetir, `02-architecture/adr/0007-i18n-next-intl.md`
(la decisión y sus alternativas) y `conventions.md` (las reglas de nombres derivadas de esta
arquitectura). Este documento es la referencia de *cómo funciona el sistema hoy*, análogo a
`03-data/sql-model.md` para el esquema de base de datos.

## Estado

**Implementado** (retrofit sobre Etapa 3.1, ver `code-walkthrough.md`). Locales activos: `es`
(default) y `en`. Arquitectura preparada para agregar locales adicionales sin tocar componentes
ni rutas.

## Por qué existe este documento aparte del ADR

ADR 0007 registra la decisión y la justifica frente a alternativas — es el registro histórico,
no se reescribe. Este documento describe el sistema tal como quedó construido, y se actualiza
cada vez que algo del mecanismo cambia (un namespace nuevo, una regla nueva de dónde va cada
string) — mismo principio que separa `02-architecture/adr/000X-*.md` de
`02-architecture/architecture.md`.

## Piezas del sistema

### 1. Locale en la URL, no en cookie/sesión

Todo el árbol de páginas vive bajo `src/app/[locale]/...`. Una URL sin locale (`/`) se resuelve
por middleware antes de renderizar cualquier página.

**Por qué:** el proyecto ya eligió PWA con compartibilidad de contenido vía Web Share API
(ADR 0001). Un link a un álbum debe abrir en el idioma correcto sin depender de que el
dispositivo receptor tenga la cookie de quien lo compartió. Ver ADR 0007 para el detalle
completo de esta justificación.

### 2. `src/middleware.ts` — detección y redirección

Intercepta toda request, determina el locale (negociación de `Accept-Language`, con fallback a
`es`) y redirige a la ruta prefijada correspondiente. No requiere lógica de negocio propia — es
configuración declarativa de `next-intl` sobre los locales definidos en `routing.ts`.

### 3. `src/i18n/routing.ts` — la fuente única de verdad de qué locales existen

```ts
export const routing = defineRouting({
  locales: ["es", "en"],
  defaultLocale: "es",
});
```

**Este archivo es el único lugar del código que necesita tocarse para agregar un locale nuevo.**
Agregar `"pt"` a ese array, más el catálogo de mensajes correspondiente (§5), es la totalidad
del trabajo de código — ningún componente, ninguna página, ningún test se modifica. Esto es lo
que hace la escalabilidad real, no aspiracional: el costo de un locale nuevo es proporcional al
trabajo de traducción, no al trabajo de ingeniería.

### 4. `src/i18n/request.ts` — carga de mensajes en Server Components

Resuelve, para el locale de la request actual, qué archivos de `messages/` cargar. Es la pieza
que permite que las páginas (`search/page.tsx` y sucesoras) obtengan texto traducido sin ser
Client Components — preservando la decisión ya tomada en `01-frontend-architecture.md` de usar
Server Components para el primer render.

### 5. `src/i18n/navigation.ts` — wrapper de `next/navigation`

Reexporta `Link`, `useRouter`, `redirect` con el mismo API de `next/navigation`, pero
locale-aware: toda navegación programática preserva automáticamente el locale activo.

**Regla de código, no solo de estilo:** ningún componente importa `useRouter`/`Link` directo de
`next/navigation`. Siempre desde `src/i18n/navigation.ts`. La razón concreta es el bug que este
wrapper evita: sin él, `router.push('/artista/${id}')` desde un usuario en `/en/search` lo
devuelve a una ruta sin prefijo de locale, perdiendo el idioma silenciosamente — exactamente el
tipo de bug que no aparece en desarrollo manual en español pero rompe la experiencia en
cualquier otro locale.

### 6. `messages/{locale}/{namespace}.json` — los catálogos de texto

Estructura:

```
messages/
├── es/
│   ├── common.json
│   ├── catalog.json
│   └── errors.json
└── en/
    ├── common.json
    ├── catalog.json
    └── errors.json
```

**Namespaces por dominio, no por página.** `common.json` es identidad de la app y acciones
genéricas (usado por cualquier componente); `catalog.json` agrupa los flujos del catálogo por
sub-namespace (`search` hoy; `artist`, `album` cuando se construyan en 3.2/3.3); `errors.json`
es un caso especial (§7). Esta organización espeja la misma lógica que ya usa el proyecto en
otras partes: `docs/` por capa numerada, `schemas.ts` por contrato de API — un namespace nuevo
se agrega cuando aparece un dominio nuevo, no una página nueva.

**Regla de completitud:** todo locale activo debe tener exactamente las mismas claves en cada
namespace. Un test unitario (`messages.consistency.test.ts`) compara `Object.keys` de cada
namespace entre `es` y `en` recursivamente y falla si hay claves faltantes en cualquiera de los
dos. Esto es lo que impide que un locale nuevo quede a medio traducir sin que CI lo note — sin
este test, un desarrollador puede agregar una clave a `es/catalog.json` y olvidar
`en/catalog.json`, y el fallback silencioso de next-intl (mostrar la clave cruda o el string en
el locale default) pasaría desapercibido hasta que un usuario en inglés lo reporte.

### 7. `errors.json` — indexado por `ErrorCode`, no por página

A diferencia de los otros namespaces, `errors.json` no se organiza por dominio de UI sino que
espeja 1:1 el enum `ErrorCode` de `src/lib/api/schemas.ts` (`docs/04-api/errors.md`):

```json
{
  "ARTIST_NOT_FOUND": { "title": "...", "description": "..." },
  "INTERNAL_ERROR": { "title": "...", "description": "..." }
}
```

**Por qué separado de `catalog.json`:** el mismo `code` (`INTERNAL_ERROR`, por ejemplo) puede
originarse desde cualquier pantalla que consuma la API — búsqueda, perfil de artista, detalle de
álbum. Centralizarlo evita que cada componente reinvente su propio mapeo de errores (que es
exactamente lo que hacía `SearchForm.tsx` antes del retrofit, con un objeto `ERROR_MESSAGES`
local). Cualquier componente nuevo que consuma `ApiError.code` reutiliza este namespace sin
duplicar nada — la fuente de verdad sigue siendo el catálogo de códigos en `schemas.ts`; este
archivo solo le pone texto por locale.

## Reglas de dónde va cada string

| Tipo de texto | Vive en | Ejemplo |
|---|---|---|
| Identidad de la app, acciones genéricas | `common.json` | nombre de la app, "Reintentar" |
| Texto específico de un flujo de catálogo | `catalog.json`, sub-namespace por flujo | `search.fieldLabel`, `artist.discographyTitle` |
| Mensaje asociado a un `ErrorCode` de la API | `errors.json`, indexado por código | `ARTIST_NOT_FOUND.title` |
| Dato del catálogo musical (nombre de artista, título de álbum, bio) | **No se traduce.** Se muestra tal cual llega de MusicBrainz | — |

Esta última fila es una decisión de producto explícita, no un olvido: i18n aplica solo al
*chrome* de la interfaz, nunca a los datos del dominio musical — anotado también en
`01-domain/business-rules.md` / `05-features/catalog-browsing.md` para que no se lea como
alcance incompleto.

## Regla de `components/ui/`: agnóstico también de i18n

`components/ui/` (`Button`, `Input`, `Skeleton`, `EmptyState`, `ErrorState`) es, por diseño desde
`01-frontend-architecture.md`, agnóstico de dominio. Extiende esa misma regla a i18n: **ningún
componente de `ui/` importa `useTranslations` ni conoce el locale activo.**

`title`/`description` en `ErrorState` y `EmptyState` son props **requeridas**, nunca con default
hardcodeado. El texto ya traducido se resuelve en el componente que sí conoce el dominio y el
locale (`SearchForm`, y los componentes de `catalog/` que sigan), usando `useTranslations`, y se
pasa hacia abajo. Esto evita el bug silencioso de un componente `ui/` devolviendo texto en
español aunque el locale activo sea inglés porque nadie pasó el prop explícito — el compilador
lo atrapa en vez de un usuario.

## Testing

- `src/test/i18n-test-utils.tsx` expone `renderWithIntl(ui, locale?)`: envuelve en
  `NextIntlClientProvider` con los mensajes del locale (default `es`) y reemplaza `render()` de
  Testing Library en todo test de componente.
- Los tests de componente hacen aserciones sobre el **texto real renderizado**, leído desde
  `messages/es/*.json` en el propio test — no sobre claves abstractas. Esto mantiene el valor
  real del test (verifica comportamiento visible) sin que quede desactualizado si cambia la
  copy: al importar del mismo catálogo que usa el componente, ambos se mueven juntos.
- El mock de navegación en tests apunta a `src/i18n/navigation.ts`, no a `next/navigation`
  directo, siguiendo la regla de §5.

## Cómo agregar un locale nuevo (referencia rápida)

1. Agregar el código de locale a `routing.ts` (`locales: [...]`).
2. Crear `messages/{locale}/{common,catalog,errors}.json` con las mismas claves que `es/` —
   traducidas.
3. Correr el test de consistencia de claves (§6) para confirmar que no falta ninguna.
4. `pnpm run typecheck && pnpm run lint && pnpm run test && pnpm run build`.

Ningún componente, página, o test se modifica. Si en algún punto agregar un locale *requiere*
tocar código fuera de `messages/` y `routing.ts`, es señal de que algo violó la separación
descrita en este documento y debe corregirse ahí, no en el locale nuevo.
